What I learned using agentic AI tools to develop an app

Xie Jiayu Dias
· June 11, 2026 · 3 min read
artificial-intelligenceprogrammingtechnologymobile-app-developmentagentic-ai

Is AI ready to replace developers once and for all?

I kept hearing that AI had made developers obsolete, that anyone could ship an app with a single prompt. I wanted to find out for myself.

For the records, I don’t have backend/full-stack background. But over the past few weeks, I built an app that connects people to go for a running/walking together [more to come about its funcionalities], using AI as my coding partner. It took more than 50 bug fixes to get it landed. Here are my thoughts about the “AI taking over dev jobs” debate and what didn’t go as expected.

React frontend. Express backend. PostgreSQL. Real-time chat via Socket.io. Auth, cloud storage, separate deployments for frontend and backend.

AI wrote a huge amount of the code. And still, it took more than 50 mitigation attempts across about 11 different failure categories before I was able to make the first version of the app go live.

Some of what went wrong:

→ The preinstall script used Unix syntax. My machine runs Windows. The AI didn’t anticipate that upfront, neither I knew that was a relevant information to be added in the prompt.

→ Vercel kept trying to deploy the wrong part of the monorepo. It took more then 10 attempts and careful manual intervention to untangle the deployment config.

→ A blank screen on the live app. No error was showing, just a blank page. Turned out a single missing environment variable (`VITE_CLERK_PUBLISHABLE_KEY`) was silently killing the whole frontend.

→ “Failed to fetch” on every API call, because the deployed frontend was pointing at itself instead of the backend on a different domain.

→ The database CLI wouldn’t read the `.env` file. The schema path broke on Windows. The build tool was missing a platform-specific binary.

Of course, none of these bugs were hard to diagnose, especially when you have an AI chat by your side. But identifying them required knowing what questions to ask, which concepts were behind, such as what a monorepo is, what environment variables do, why SPA needs URL rewrites and why a free-tier server goes cold. I found out that having some software engineering background was equally helpful when deciding which solution path is the most suitable for each case.

AI did an awesome job generating the code. However, it couldn’t always tell me why something wasn’t working in my specific environment, with my specific deployment constraints. To support this statement, I have been changing some connection route as per AI suggestion, in an attempt to resolve an error of monorepo deployment. However, that generated a new error, which was solved when you go back to the original connection. This back-and-forth setting went on for some more failures until I detected that I was running in a dead lock.

The gap, between a “generate the code” prompt and “understanding the system”, is where I believe the developers/system architects live.

AI is an incredible tool. It enabled someone like me to ship something real, and so much faster when compared to traditional delivery teams. However, it demanded a lot of effort to push myself into learning a huge of programming skills, and getting familiar with the dev tools. My conclusion is: developers are still needed, and they should be getting more and more experience with AI tools.

I Built a RAG System That Reads Explainability Research For Me

Xie Jiayu Dias
· August 6, 2026 · 6 min read
llmairesearchllm-applications

How I turned “I can’t keep up with this field” into my LLM Zoomcamp capstone project: a daily digest for explainable AI system, pulling data from arXiv, Anthropic, and OpenAI.

As part of my transition into AI research, I’ve felt overwhelmed by how much there is to catch up on. Most of the time I don’t even know whether the method I’m studying or trying to replicate is actually state-of-the-art, because the field keeps evolving so fast.

Explainability research is a good example of the problem. The work I care about (mechanistic interpretability, feature attribution, model transparency, the alignment-adjacent edges of all three) moves quickly and lives everywhere. Some of it lands on arXiv as preprints. Some of it shows up on Anthropic’s research page. Some of it goes out through OpenAI’s feed. Not mentioning that a lot of those works live in other labs/frontier companies’ feed. There’s no single place to track it all, so “staying current” means remembering to check several sites and hoping I didn’t miss the one that mattered.

So, for the capstone project of the LLM Zoomcamp (by DataTalks.Club), I decided to build a system reads the explainability research for me. Something I could keep using in my daily research routine, not a notebook I’d run once for a grade.

I called it XAI Daily Digest. It’s a daily journal of sorts for checking the latest advancements in explainable AI. And because it’s a RAG system underneath, I can also chat with it to look up definitions and concepts I’m not yet familiar with, grounded in the papers themselves.

The repository is here: github.com/xiejiayu95/research-assistant

What it actually does

Two things, really.

You can ask it questions about everything it has collected, such as “What is mechanistic interpretability, and how does it differ from feature attribution methods?”, and it answers from the retrieved research with inline [1] [2] citations that link straight back to the source papers and posts. Given that the whole subject is explainability, the citations aren’t decoration; they’re the point. If a tool is going to tell me what the latest transparency research says, it had better show me exactly where each claim came from.

Or you can ask it to generate a digest: a themed summary of everything ingested in the last 24 hours, with the same citation treatment. That’s the “daily journal” use case: open it in the morning, see what’s new across all three sources, click through to whatever looks worth reading in full.

How it works

Under the hood it’s a full pipeline, not a single script, and building each stage properly is where most of the learning happened.

Ingestion. Every day, the system pulls XAI-relevant content from three sources: the arXiv API (filtered to interpretability and explainability papers across cs.AI, cs.LG, cs.CL, and cs.CV), Anthropic’s research index page, and OpenAI’s research feed. I selected these three sources manually for now — they’re the ones I most read — and the design leaves room to add more. The ingestion runs as a Prefect flow served on a daily cron schedule inside its own container, so it’s a real orchestrated pipeline rather than something I have to remember to trigger. New items are deduplicated and logged in Postgres, then chunked, embedded, and written to the vector store.

Retrieval. This is the part I’m happiest with. Each chunk gets two representations in a single Qdrant collection: a dense vector from OpenAI’s text-embedding-3-small, and a sparse BM25 vector via fastembed. At query time the system fuses both with Reciprocal Rank Fusion — hybrid search — so it benefits from semantic similarity and exact keyword matching instead of forcing a choice between them. The fused results are then re-ranked with a local cross-encoder through FlashRank. And before any of that, the user’s question is rewritten by the LLM to broaden recall.

Query rewrite → hybrid search → rerank → answer

Grounding. Retrieved chunks go to an OpenAI chat model (gpt-4o-mini by default, configurable) with a prompt that enforces citations, and the answer comes back with a “Sources” expander tying every claim to a paper or post.

Evaluation. I didn’t want to pick these design choices by vibe, so I measured them. For retrieval, an LLM generates a golden set of roughly sixty questions — one per sampled chunk — and I compare three strategies against it by Hit Rate@5 and MRR@5: dense-only vector search, hybrid (dense + sparse RRF), and hybrid plus reranking. For generation, I compare three prompt-and-model variants — a baseline prompt on gpt-4o-mini, a citation-enforcing prompt on gpt-4o-mini, and the baseline on gpt-4o — scored by an LLM-as-judge on relevance and faithfulness. The design decisions are backed by numbers I can point to.

Monitoring. Thumbs-up/thumbs-down feedback from the app, answer latency, and ingestion volume by source all flow into a Grafana dashboard that populates automatically as the app is used.

Reproducibility. The whole thing runs on Docker Compose. Clone the repo, set an OpenAI key, docker compose up — Postgres, Qdrant, Grafana, the ingestion container, and the Streamlit app come up together. You don’t need any of the course material to run or evaluate it; it’s a standalone app.

Here’s the shape of it end to end:

arXiv API  ─┐
Anthropic  ─┼─▶ ingestion (Prefect) ─▶ Postgres (metadata, dedup, logs)
OpenAI     ─┘                        └▶ Qdrant (dense + sparse hybrid vectors)
                                              │
                                              ▼
                         query rewrite → hybrid search → FlashRank rerank → OpenAI chat
                                              │
                              ┌───────────────┴───────────────┐
                              ▼                               ▼
                     Streamlit app (Ask + Digest)     Grafana (monitoring)

The stack: OpenAI · Qdrant · Postgres · Prefect · Streamlit · Grafana · Docker Compose.

What I’d tell you before you rely on it

It ingests abstracts and blog summaries, not full paper text. That’s enough for a daily-digest use case and for surfacing what’s new, but a deep question about a specific paper’s methodology will only be as good as what the abstract contains.

The arXiv relevance filter is a heuristic — a keyword check for interpretability-related terms — so it will occasionally let through a paper that mentions “interpretable” only in passing, or miss one that’s on-topic but phrased differently. An LLM-based relevance classifier is the natural next step.

And the Anthropic ingestion scrapes their public research index because there’s no RSS feed to consume; if that page’s markup changes, that fetcher will need updating. Trading robustness for coverage was a deliberate call, but it’s a real dependency.

The part that stuck with me

Building a RAG system about interpretability changed how I thought about the citation layer. In most RAG demos, citations are a nice-to-have you bolt on at the end. Here, tracing every generated sentence back to a specific source felt like the actual subject of the project leaking into its design — the same traceability that explainability research is chasing inside models, I was chasing inside my own tool. Legible isn’t the same as objective, and a system that shows its sources isn’t automatically right. But it’s the difference between an answer I can check and one I just have to trust.

If you want to look at the code, run it, or tear the design apart, it’s all here: github.com/xiejiayu95/research-assistant.

Huge thanks to Alexey Grigorev and DataTalks.Club for a free course that genuinely goes all the way from “call an API” to “ship an orchestrated, evaluated, monitored system.” If you’re working on interpretability, or building production RAG, I’d love to compare notes.
